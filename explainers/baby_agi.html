History of LLMs: BabyAGI, the first steps towards reasoning and agentic AI

Give BabyAGI a goal and it writes its own to-do list, works through it one task at a time, and keeps adding new tasks based on what it just did. This is the original 2023 script by Yohei Nakajima, rebuilt as a web page. Instead of calling GPT-3.5 through the OpenAI API, every step is run by Qwen3-1.7B on your own graphics card.

Can your device run it?

The model runs on your own graphics card, not on a server. It needs a GPU with about 8 GB of memory to run properly.

What BabyAGI is

In the spring of 2023, a few weeks after GPT-4 came out, Yohei Nakajima posted a Python script of roughly 150 lines that he called a task-driven autonomous agent. It was renamed BabyAGI, got tens of thousands of GitHub stars within weeks, and together with AutoGPT it kicked off the first wave of "AI agents". The name is a joke: nothing about it is general intelligence. The interesting part is how little it takes: three prompts and a while loop.

Each pass through the loop calls the language model three times, each time with a different job:

  • execution agent gets the objective, one task and the names of up to five earlier tasks, and is asked to "perform" the task. Whatever text comes back counts as the result.
  • task creation agent reads that result and writes a numbered list of new tasks that must not overlap with the ones still waiting.
  • prioritisation agent gets the whole waiting list and returns it reordered, with the most essential tasks first.

Between these calls there is no intelligence at all, only string handling. Python splits each answer on newlines, keeps lines that look like 3. Some task, strips punctuation, and puts the result in a queue. Open the prompt and parsed parts of the agent log above to see both halves: what the model was asked, and what the code made of its answer.

Things to watch for

  • It cannot actually do anything. The agent has no tools, no web search and no way to check anything. If a task says "research the best textbooks", the execution agent simply writes something that sounds like research. Every "result" is the model's imagination.
  • The list rarely gets shorter. Each finished task usually produces several new ones, so the queue grows faster than it is worked off. The original ran forever unless you pressed Ctrl-C.
  • Memory is thinner than it looks. Earlier results are stored, but the execution agent is only shown the names of earlier tasks. So it regularly redoes, or contradicts, work it has already done.
  • The code trusts the model completely. The prioritisation prompt says "Do not remove any tasks", but whatever list comes back replaces the queue. When the model drops or invents a task, the log flags it.
  • Try a vague objective. "Solve world hunger" shows most clearly how an agent without tools and without a stop criterion drifts into ever more abstract tasks.

Almost every agent framework since, including the coding agents in use today, is an answer to one of these problems: give the model real tools, feed the actual results back in, and decide explicitly when the goal has been reached.

What is different from the original

The prompts, the parsing and the order of the loop are copied from babyagi.py. A few things had to change to run it in a browser tab:

  • The model. GPT-3.5-turbo behind the OpenAI API is replaced by Qwen3-1.7B, a model with 1.7 billion parameters, compressed to 4 bits. Qwen3 can "think" before it answers; that mode is switched off so each agent answers directly, as GPT-3.5 did.
  • Sampling. The original used temperature 0. Small models tend to repeat themselves when decoding greedily, so this page uses Qwen's recommended settings (temperature 0.7, top-p 0.8, top-k 20). Two runs with the same objective will therefore turn out differently.
  • Memory. The original stored results in a vector database (Chroma or Pinecone) with OpenAI embeddings, and looked up the five results closest to the objective. Here the same lookup is done with simple word-overlap similarity, which avoids downloading a second model.
  • Parsing. The prompts show the list format as #. First task. GPT-3.5 understood that the # stands for a number; Qwen3-1.7B often writes the # literally. The original parser needs a digit before the period and would throw those lines away, ending the run after one task. This page accepts a literal # too, and says so in the log whenever it happens.
  • Repetition. Left alone, the small model tends to write the same few tasks again and again until it runs out of tokens. So the task creation agent is cut off as soon as it repeats a line, and tasks that are already on the list are not added a second time. The log shows when either happens.
  • Limits. The loop stops after a set number of iterations instead of running forever, and the task creation and prioritisation agents are capped at 300 tokens (their lists are short) instead of 2000.

How this page runs a 1.7B model without a server

The page loads Transformers.js, which runs ONNX models through ONNX Runtime Web. With WebGPU the matrix multiplications run on your graphics card, which is what makes a model of this size usable at all: roughly ten times as many parameters as the GPT-2 explainer. The weights are a q4f16 export (4-bit weights, 16-bit activations) of about 1.4 GB. The browser downloads them once and caches them, so a second visit only has to load them onto the GPU.

One practical detail: the official onnx-community export stores the whole model in a single 1.4 GB .onnx file. ONNX Runtime Web has to read that file into WebAssembly memory before it can hand the weights to the GPU, and it runs out of memory (std::bad_alloc). This page loads a copy of the same export with the weights split off into a separate .onnx_data file, which ONNX Runtime Web loads separately, so it fits.

The model runs in a Web Worker, so the page stays responsive while it generates and the Stop button can end a generation between two tokens. Everything is static: GitHub Pages only serves files, and your objective never leaves your computer.
